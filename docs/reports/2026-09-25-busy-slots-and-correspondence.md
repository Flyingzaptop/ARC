# Занятые версии GPU и первая автоматически найденная связь CPU/GPU

Продолжение `8a71a96`. Поддержанный класс ручного адаптера не расширялся. Новый FPS-бенчмарк не проводился: принятый indirect-путь остаётся контрольным образцом.

## Живая проверка трёх занятых версий

Добавлен отключённый по умолчанию `ARC_INDIRECT_BUSY_TEST`. Это **реальный отложенный GPU-потребитель**, а не подмена значения `GetCompletedValue`.

Отдельная native D3D12 queue ждёт сначала разрешение теста, затем завершение графических потребителей каждого кадра. На ней поставлены чтения sidecar upload, record upload, draw templates, packed output и indirect arguments трёх версий. Consumer fence ARC сигналится этой очередью после чтений. Графическая очередь игры не ждёт тестовую очередь, поэтому основной цикл может исчерпать все три версии и перейти на CPU.

| Проверка | Результат |
|---|---:|
| Удержанные версии | 3 |
| Задержка GPU-потребителя | 415,228 мс |
| CPU fallback из-за занятых версий | 4 |
| Проверенные версии после освобождения | 3 |
| Побайтно проверено отложенным потребителем | 11 773 680 байт |
| Ожидание метаданных CPU со стороны ARC | 0 мс |
| Indirect draw-команды после освобождения +100 мс | 372 |

Ни одно сравнение не выявило перезаписанные данные. В частности, sidecar содержит поколение кадра, поэтому тождественность некоторых других полей между соседними кадрами не скрывает преждевременное использование новой версии. Fallback исполняется до reset allocator и записи upload. После освобождения проверка снова допускает indirect.

Тест выполнен один раз, ограниченный процесс завершился штатно. Он диагностический: дополнительные копии и CPU-сравнения не являются измерением производительности. Существующие ожидания самого движка не удалялись; со стороны ARC нет нового CPU fence-wait для освобождения версии.

## Что автоматизировано

Добавлен `scripts/cpu_gpu_correspondence.py`: offline-детектор для режима обучения. Он получает только два набора **сырых байтов** GPU-буфера и окон CPU-памяти. На входе нет имени движка/поля, известных strides, смещений поля или адреса массива объектов.

CPU-кандидаты собраны через `VirtualQuery` и `ReadProcessMemory`: committed private RW regions, до 64 окон по 256 KiB. Исключены текущий mapped upload и собственные собранные вручную expected/previous-массивы аудитора. Снято 59 и 60 окон, общих между наблюдениями — **58**.

**Сбор ещё не полностью универсален:** GPU-кандидат `instanceBuffer` для этого эксперимента выбран вручную в адаптере. GPU-снимок получен после завершения реальной копии и GPU; сырые CPU-кандидаты и расположение поля внутри них не выбирались по исходникам. Эта оставшаяся ручная часть явно указана в контракте и машинном результате.

Алгоритм:

1. Выбирает непостоянные 12-байтовые float-векторы из начала GPU-снимка, отбрасывая многократно повторённые константы.
2. Ищет совпадения в CPU-окнах и выдвигает модели `CPU_offset + i × CPU_stride ↔ GPU_offset + i × GPU_stride`.
3. Проверяет модель на 64 индексах каждого кадра: 0–31 и отдельном диапазоне 64–95, не использованном при поиске.
4. Требует изменения данных между кадрами. Отмечает варианты с пропуском каждой второй/третьей записи как aliases, а не новые задачи.

Ограничения: только точные 12-байтовые совпадения, GPU stride до 1024, CPU stride до 4096, ограниченный seed-диапазон. Упакованные/преобразованные значения и семантика вычислений этим методом не восстанавливаются.

## Найденный результат

Автоматически получена одна основная связь:

```text
CPU: начало обнаруженного окна + 608 + i × 576
GPU:                         80 + i × 256
Ширина совпадения: 12 байт
```

Детектор исследовал 58 окон, выбрал 27 seed-векторов и проверил 13 моделей за **1,30 секунды**. Основная связь совпала на 64 записях каждого из двух кадров; все 64 изменились между наблюдениями. Ещё три результата — её subsample-aliases, не три дополнительных связи.

**Только после обнаружения** независимый oracle по исходникам подтвердил: найденное CPU-поле — `ObjectComponent::center`, а GPU-поле — `ShaderMeshInstance::center`. CPU stride 576 и GPU stride 256, адрес и смещение совпали с oracle. Имя `center` сам детектор не выводит.

Это поле не используется для нового разрешения переноса. Fade/radius/stencil, которыми пользуется текущая упаковка, остаются ручными соответствиями; совпадение постоянных значений не было выдано за их обнаружение.

На реальных снимках повторный запуск с переименованными файлами и UUID вместо адресных идентификаторов получил те же связи. Четыре адресных Python-теста прошли: восстановление неизвестных strides/offsets, инвариантность к именам, отказ на устаревшем GPU-снимке и отказ на неизменных константах.

## Что остаётся ручным

В существующий `experiments/record-pack-indirect/contract.json` добавлен явный список:

- границы CPU-пакета и формат его 16-байтовых записей;
- выбор/идентичность GPU instanceBuffer;
- GPU offsets fade/radius/stencil;
- производитель sidecar и завершение его jobs;
- CPU-потребители LOD/stencil/material/PSO и GPU-потребитель indirect;
- момент публикации upload и завершение потребителей.

Детектор доказал **наблюдаемое побайтное соответствие на проверенной выборке**, а не причинную зависимость, владение памятью или корректность замены для всех будущих входов. В результате сохраняется `replacement_allowed=false`. Автоматический перенос ARC не объявляется выполненным.

## Стоимость обучения

Это отдельный медленный capture, не игровой режим. CPU-снимки занимают 15 466 496 и 15 728 640 байт; GPU-снимки — по 16 MiB. Для завершённого GPU readback аудитор использует `WaitForGPU`; **это не часть busy-slot теста или производительного indirect-пути**.

Наблюдавшийся интервал кадра первого захвата — **3 018 мс**, включая загрузку сцены. Следующий кадр — **266 мс**, затем кадр завершения аудита — **156 мс**. Загрузку и собственную стоимость первого capture здесь отдельно не разделяли. Эти данные не позволяют назвать обучение незаметным для игры; заметное замедление разрешено только в режиме обучения. Затраты постоянного игрового режима не оптимизировались.

Полную историческую матрицу не повторяли. Новые native-прогоны: один busy-slot diagnostic и один capture, по 12 секунд запрошенной работы, жёсткий лимит процесса 60 секунд. Коммерческие игры не запускались. Условия мощности не менялись и не использовались как критерий приёмки.
