# Контрольный перенос CPU → GPU: Wicked

> **Поправка 24 сентября:** в этой исторической версии `replaced` захватывался по ссылке и выходил из области видимости до `Wait(ctx)`. Проверка до CPU-задач не исключала ошибку конечного списка. Эти замеры не подтверждают корректность исправленной сборки. См. [исправление и новые проверки](2026-09-24-replaced-lifetime-fix.md).

Результат: на измеренном интервале отправки кадров оба варианта проигрывают оригиналу. Улучшение плавности не подтвердилось. Это отрицательный результат узкого эксперимента; полный O2 gate по завершённым GPU-кадрам не измерялся.

## Что реально заменено

- C: GPU вместо CPU проверяет frustum/layer mask для всех 65 536 объектов.
- W: дополнительно GPU собирает список видимых объектов; исходная CPU-компактизация и её атомики пропускаются. Остальные CPU-эффекты и потребители сохранены.
- CPU: отдельный последовательный вызов исходной функции по массиву; стоимость чистого вычисления без atomics/wait, но это НЕ измерение его прежней параллельной критической задержки.
- N: новая сборка с выключенным переносом. A: сохранённый исходный EXE, без DLL ARC.

## Цена переноса

Чистый последовательный CPU-проход: **0,826 мс**. GPU predicate kernel: **0,0057–0,0061 мс**, весь перенос: **1,134–1,159 мс**. У расширенного пакета ядро **0,0083 мс**, весь перенос **1,186–1,193 мс**. Расширенный пакет улучшил общую CPU-каденцию относительно первого GPU-варианта, но собственная стоимость передачи выросла.

Для W: упаковка/копирование на upload около 0,343 мс, подготовка/отправка 0,184 мс, ожидание fence 0,596 мс, чтение/копирование результата 0,065 мс. Kernel time находится внутри ожидания; складывать его второй раз нельзя. Передача на вызов: 2 МиБ входов плюс 256 КиБ ответа C или 512 КиБ + 4 байта ответа W. Собственные основные буферы W: около 5 МиБ D3D12-ресурсов плюс 512 КиБ CPU-результата, без драйверных/PSO расходов.

Для сравнения W с A2/A3 диагностический порог 1.090 мс, консервативный выигрыш **-1.031 мс** — отрицательный. Это расчёт по CPU cadence, не подмена отсутствующего complete-frame gate.

## Корректность и границы

Сравнены 31 522 816 ответов узкого варианта и 32 309 248 ответов расширенного: ноль несовпадений маски. Проверка расширенного списка: ноль пропущенных/лишних/повторяющихся индексов. Проверки выполнялись в отдельных oracle-запусках и выключены в C/W. Порядок списка параллельный; одинаковый порядок с оригиналом не заявляется.

Проверены реальные входы текущей сцены; нет приёмки для произвольных NaN/denormal, хвостовых групп, всех игр или универсального ARC. Код использует D3DCompile cs_5_0 / IEEE strictness для небольшого диагностического шейдера, исходная CPU-функция сверяется напрямую.

Первый A1 не дал данных и исключён, сохранён для аудита. Последующие baseline по штатному пути выполнены тем же исходным SHA. Сборка требует существующий MT build-wicked-generic; начальные ошибки пути solution/includes/CRT сохранены в логах. Изменения окружения/качества для получения выигрыша не применялись.

## Почему не просто отправить ещё

Исследована соседняя RunObjectUpdateSystem: там действительно есть преобразование AABB, подготовка матриц/GPU-instance data, но между ними расположены CPU LOD, ECS/материалы, occlusion, ресурсы и другие потребители. Автоматически считать весь этот участок чистым GPU-ядром нельзя.

Эксперимент показывает быстрый GPU, но не бесплатный CPU↔GPU обмен. Для следующей гипотезы нужен более дорогой естественный пакет, желательно с результатом, который уже нужен GPU и не требует немедленного readback. Его необходимо отдельно выделить и измерить. Текущий перенос отключён; расширять его вслепую после отрицательного результата не продолжаем.

Это не доказательство невозможности полезного переноса других задач. Универсальный экстрактор не разрабатывался, прежний O1 остаётся невыполненным.

## Следующий эксперимент отложен по запросу пользователя

Текущий пакет выполняется каждый кадр, а не один раз за сессию. Но это один
синхронный пакет: CPU ждёт результат перед продолжением обработки. Пользователь
предложил очередь максимально крупных полезных пакетов и увеличение объёма
переноса при свободной GPU-мощности. Очередь и перекрытие передачи/вычислений
пока НЕ реализованы и не проверены. Размер/число пакетов должны ограничиваться
реальными зависимостями и полной стоимостью, а не одной разностью CPU/GPU frametime.
Синхронные результаты этого отчёта не доказывают результат будущей очереди.
