# Большой пакет с существующими GPU-данными: реальная замена, но общий выигрыш пока не подтверждён

Продолжение `9a1503f`. Реализован **исследовательский адаптер Wicked по исходникам**. Соответствие полей не обнаруживается автоматически ARC. Сортировка остаётся исходной CPU-сортировкой, включая порядок равных ключей.

## Что исполняется

1. Исходные отсортированные 16-байтовые записи копируются непосредственно в постоянный upload-буфер. Сбора 48-байтовых записей больше нет.
2. GPU читает актуальный `Scene::instanceBuffer`: fade/radius/stencil. Существующая загрузка этого буфера перенесена раньше на ту же graphics queue; её прежняя копия и барьеры пропускаются. Дополнительной полной загрузки массива объектов нет.
3. В существующем job производителя записывается 12-байтовый sidecar: **точная float32-прозрачность, CPU LOD и результат исходного `alphaRef < 1`**. Половинная точность цвета/alpha-test не используется для восстановления этих значений. Дополнительного обхода объектов нет; есть одна сплошная копия sidecar в постоянную UPLOAD-память, которую GPU читает напрямую.
4. Пять GPU-стадий вычисляют значения/маски, локальные и глобальные префиксы, границы групп, стабильную упаковку и метаданные. Промежуточные массивы остаются на GPU.
5. CPU получает **8 208 байт метаданных** и вызывает исходный `batch_flush`. Графические команды действительно используют GPU-буфер упакованных указателей. В режиме замены исходный цикл упаковки не выполняется.

Это два пакета на кадр, по одному для main/prepass. Типичный пакет — 65 344 записи; первый — 65 536. На пакет загружается 1 045 504 байта записей; sidecar для 65 536 объектов — 786 432 байта на кадр. Упакованный результат обратно на CPU в рабочем режиме не копируется.

Предел эксперимента: 65 536 записей, 256 групп, 16 camera bits, два поддержанных прохода. Превышение/неподдержанный проход сохраняет CPU-путь. Forward-light AABB merging не перенесён. Это не универсальная замена всех вызовов RenderMeshes.

## Корректность и синхронизация

В отдельном живом oracle-прогоне проверено **15 944 320 записей**, все слова результата и все поля метаданных совпали. Проверяются mesh, LOD, stencil, alpha flag, offset, count, начало/конец группы. Дополнительно прошли пять GPU-тестов размеров 1/255/256/257/65536 с несколькими группами, нулевыми и многобитовыми масками, прозрачностью и alpha-test.

Границы групп рассчитываются до отбрасывания полностью затухших записей, как в оригинале. Порядок записей и порядок битов камеры сохранены. Пустые группы не создают draw.

Ранний upload и пакеты отправляются в настоящую graphics queue Wicked после уже поставленных межочередных зависимостей предыдущего кадра. CPU ждёт fence конкретного пакета перед потребителем метаданных. Для main/prepass отдельные буферы в трёх кадровых слотах; повторное использование упорядочено той же очередью. **`WaitForGPU` и полный readback instanceBuffer отсутствуют.** Полный readback выходных указателей включён только в oracle-режиме.

Машинно-читаемые границы покрытия и предпосылки: `experiments/record-pack-gpu/contract.json`. Проверено на выбранной динамической сцене; отсутствие изменений полей после производителя — свойство разобранного пути Wicked, не общее доказательство для произвольной игры.

При разработке первое обращение к предыдущему элементу вызвало GPU device hang: HLSL мог вычислять `key(i-1)` и для первого элемента. Индекс теперь ограничен до обращения к памяти; нулевая/крайняя группа проверяется отдельными тестами. Успешные финальные запуски не имели device-loss.

## Экономика

RTX 3060 Laptop, i7-11800H. Одна и та же сборка, сцена 18 и управление камерой. Порядок: CPU → только sidecar → замена → замена → sidecar → CPU. Каждый процесс — 20 секунд, лимит 60 секунд; steady-окно 6–19 секунд. Медленные кадры внутри окна не исключались. Исходный CPU-режим содержит ту же диагностическую обвязку, но не исполняет GPU-замену.

### Стоимость пакета в живом приложении

Средние по двум прогонам; миллисекунды. Времена GPU находятся внутри ожидания, **складывать их с fence wait нельзя**.

| Измерение | Время |
|---|---:|
| Исходный цикл упаковки, без batch_flush | 2,419 |
| Исходный batch_flush | 0,030 |
| Новый пакет: CPU copy → запись/submit → fence → метаданные | 1,310 |
| Внутри него: копирование исходных записей | 0,085 |
| Запись команд | 0,121 |
| Ожидание fence | 0,966 |
| GPU-вычисления, отдельно | 0,415 |
| GPU-загрузка записей, отдельно | 0,100 |
| GPU-копирование метаданных, отдельно | 0,003 |
| Сохранённый CPU-потребитель batch_flush | 0,021 |
| Ранний upload: CPU-подготовка/отправка на кадр | 0,266 |

Индивидуальную стоимость 12-байтовой записи внутри job не измеряли таймером на каждом объекте: он сам исказил бы эту малую операцию. Она включена в Update и полный кадр. Контроль «только sidecar» дал 23,447 против 23,314 мс, но разброс его повторов не позволяет приписать всю разницу именно записям. Повторного сбора полей в этом контроле нет.

Изолированный replay дал медиану 0,709 мс на пакет, GPU 0,360 мс. **Это не результат игры:** там нет конкурирующего рендера, а входы уже подготовлены. Решение основано на живых замерах ниже.

### Полный кадр

Это **интервал CPU между вызовами Present**, не display FPS и не время завершённого GPU-кадра. Hz — его обратная величина. Два прохода могут выполняться параллельно, поэтому экономия двух CPU-циклов не равна экономии критического пути кадра.

| Режим | Прогон A, мс | Прогон B, мс | Среднее, мс | Частота, Hz |
|---|---:|---:|---:|---:|
| Исходная CPU-работа | 23,309 | 23,320 | 23,314 | 42,89 |
| Только записи sidecar | 23,249 | 23,644 | 23,447 | 42,65 |
| Реальная GPU-замена | 23,027 | 23,195 | 23,111 | 43,27 |

Номинальная разница — **0,203 мс / около 0,9%**. В предыдущей чистой серии без нового таймера CPU-цикла исходный режим менялся между повторами примерно на 0,43 мс — больше этой разницы. Поэтому **повторяемый выигрыш выше шума не заявляется**.

p99: исходный 28,697 / 30,030 мс; замена 27,905 / 30,694 мс. Улучшения хвоста также нет оснований объявлять. В рабочем режиме реально заменено 182 441 216 записей; fallback-событий не было.

Отдельно сохранены все строки загрузки/инициализации. Первый ранний upload вместе с созданием собственных объектов занимал до 60,84 мс; полная инициализация worker PSO не входит в steady-таблицу. В одном запуске замены после 4 секунд был интервал 90,45 мс. Интервалы всего запуска до 3,3 с включают загрузку сцены, поэтому фиксированное окно «после 4 секунд» нельзя выдавать за сопоставимый steady-результат: в одном CPU-запуске туда попала загрузка. Сырые данные сохранены без удаления этих событий.

GPU-питание не фиксировалось: `nvidia-smi` возвращал N/A для power limit. Например, в первой чистой серии наблюдалось около 34–36 W в CPU-режимах и 54 W при замене. **Это не проверка при гарантированных 30 W.** Температура/частоты/мощность приложены для обоих чистых наборов. Существующая GPU-frame query Wicked не включает новую раннюю работу, поэтому её значения не названы полным GPU frametime.

## Вывод и следующий проверяемый шаг

Удалось убрать дорогой повторный сбор входов и реально заменить упаковку с сохранением потребителей. Это уже не только быстрый шейдер на собственных данных. Однако ускорение самого участка **не превратилось в убедительное ускорение кадра**.

Самое крупное измеренное ограничение нового пути — **0,966 мс ожидания метаданных на пакет**, около 74% времени пакета. Это включает исполнение GPU и предшествующую работу очереди, а не чистую стоимость readback: копирование метаданных занимает только 0,003 мс. Точное распределение ожидания между очередью и вычислениями отдельной системной трассой не установлено.

Следующий эксперимент имеет смысл только с устранением этой зависимости: оставить counts/offsets на GPU и использовать их как indirect arguments, сохранив CPU-выбор pipeline/material и порядок групп. Сначала нужно установить, какие группы CPU может подготовить без GPU-флагов и как сохранить alpha-test/LOD/stencil. Увеличение количества пакетов либо простое ускорение копирования 8 KiB эту зависимость не снимает. Новый эксперимент в этот этап не включён; текущий путь по умолчанию выключен.

## Артефакты и воспроизведение

- Код, запуск, анализатор, контракт: `experiments/record-pack-gpu/`.
- `docs/evidence/packet-gpu-20260925/raw.zip`: **72 файла**, два чистых набора CSV/конфигураций/телеметрии, вход replay и тестовые данные.
- `analysis.json`, `preceding-clean-series.json`, `manifest.json`, `gpu-tests.json`, `isolated-replay.csv`.
- Пять полных патчей Wicked и проверка точного воспроизведения instrumenter → патчи.
- Проверенная сборка: `C:/Users/r3d_flzp/ARC-Hardening-GPU/universal-optimizer/packet-gpu-timed-20260925/Tests.packet.exe`; SHA-256 в manifest.

Первый живой набор с конкурентной записью в старый CSV writer исключён. Исправление: worker сохраняет показатели в слот, главный поток публикует их в следующем кадре; эти строки имеют момент публикации, а не исходный номер кадра. Поэтому анализ использует широкое steady-окно, а не корреляцию отдельных packet-событий с соседним кадром.

Канонический EXE и пять исходных файлов внешнего Wicked восстановлены побайтно. Коммерческие игры не запускались. Автоматическое обнаружение соответствия полей и универсальный перенос ARC не объявляются реализованными.
