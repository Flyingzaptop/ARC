# ARC: собственное измерение GPU-затрат

ARC теперь сам определяет стоимость работы через DX12: без названий проходов,
подсказок движка и чтения изображения каждого кадра. Это реализованный слой
диагностики для следующей оптимизации; нового ускорения FPS в этой итерации нет.

## Результат на тяжёлой сцене

В каждом из двух захватов ARC получил 1088 интервалов за 16 кадров, различил
47 compute-шейдеров и учёл 224 косвенных вызова. Покрыто 98,91% и 99,20%
GPU-интервала кадра. Ошибок GPU, потерь из-за лимитов и пропущенных измерений нет.
Это покрытие времени в проверенной сцене, а не всех DX12-игр или всех ресурсов.

Найденные затраты в основном захвате:

| Работа | GPU-время на кадр |
|---|---:|
| Все compute-проходы | 9,19 мс |
| Из них самый дорогой отдельный шейдер | 3,96 мс |
| Отрисовка без цветовых целей с depth/stencil | 4,08 мс |
| Цветовая отрисовка | 1,68 мс |

Дорогой шейдер запускается сеткой 240×135 групп по 8×8 потоков — 1920×1080
вызовов. Его хеш одинаков в повторных запусках. Независимая сверка по GPU-времени
связала его с освещением: совпадение интервала с меткой рендерера — **99,983%**.
Эта метка используется только для проверки результата и не передаётся ARC.
Дополнительный запуск финального DLL подтвердил тот же шейдер: 4,13 мс.

## Что реализовано

- Ограниченный захват таймингов прямых и косвенных вызовов, включая compute-очередь.
- SHA-256 шейдеров, размеры групп потоков и объявления привязок ресурсов из DX12.
- Чтение только после GPU-fence; перезаписанные данные повторного запуска
  отбрасываются. Приложение не рендерится повторно ради профиля.
- Защита времени жизни при Reset, удалении команд и повторном использовании
  закрытых списков, включая использование после сохранения отчёта.
- Сверка с независимыми GPU-интервалами бенчмарка и проверки ограничения памяти.

Всего на 1088 интервалов приходится 17 408 байт значений таймеров. Скриншоты
отдельно сохраняет тестовый рендерер после измерения производительности.
Для уже записанных кэшированных списков таймеры остаются до их Reset/удаления;
в проверенной сцене они освобождаются после короткого окна захвата.

## FPS и накладные расходы

Нативные 1080p, без FSR/DLSS-апскейлинга и генерации кадров. 600 одинаковых
положений камеры после прогрева; каждый процесс работал около 15 секунд.

| Режим | FPS |
|---|---:|
| Без ARC, первый запуск | 68,31 |
| ARC, наблюдение | 68,58 |
| ARC, наблюдение и короткий профиль A | 68,25 |
| ARC, наблюдение и короткий профиль B | 68,03 |
| Без ARC, повтор | 67,04 |

Это не прирост производительности. Сам захват имеет цену: CPU-подготовка
проходов в первых 16 кадрах занимала 6,96–7,34 мс против 5,01 мс при простом
наблюдении. Поэтому сбор ограничен коротким окном. После завершения в этой
сцене не остаётся удерживаемых GPU-записей профилировщика.

На детерминированных нативных тестах результаты compute и пиксели совпадают
побитно. У тяжёлой сцены есть небольшая временная вариация GI: средняя ошибка
изображения при профилировании 0,000301; при повторе baseline — 0,000293.
Побитную повторяемость этой сцены не заявляем.

## Что дальше

Даже полное, гипотетическое устранение самого дорогого compute-шейдера дало бы
лишь около **1,36×** по измеренному GPU-интервалу. Для 2× требуется убрать около
**7,47 мс** работы. Это расчёт бюджета, а не обещание достижимого ускорения.

Следующий шаг — через DX12 разрешить реальные CBV/SRV/UAV-привязки этого шейдера
и проверить его входы, выходы и зависимости. Только затем можно реализовать
безопасную замену вычислений. Объявления ресурсов из шейдера сами по себе не
доказывают, что уменьшение Dispatch или пропуск работы допустимы. Автоматическое
принятие таких изменений пока заблокировано.

47 обычных тестов и нативные проверки прошли: точные результаты, indirect dispatch,
две разновидности очередей, перезапись кэшированных измерений, Reset при работе
GPU, обычные и приостановленные render pass, откат VRS, ресурсы/readback и ошибки
нативных API. Игры не запускались.

В архиве есть отдельные хеши DLL сравнительной серии и финального DLL. После
серии добавлен только отказ от захвата на связанных multi-node адаптерах;
финальный DLL отдельно проверен нативными тестами и полной тяжёлой сценой.
